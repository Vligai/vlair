## Executive Summary

Since the 2026-03-24 review, every prioritized item — Immediate, Next Sprint, Medium-Term, and Low Priority — has been addressed in code (see commits `46d2353`, `e56566d`, `3fbf4b7`, `43f1766`, `2d4304c`). The platform's security baseline now meets a credible enterprise floor: secret-key enforcement, security headers, salted credential hashing, token revocation, rate limiting, MFA recovery, audit rotation, and a deployment guide all exist.

The remaining work is a different shape than before. The **easy correctness issues are gone**; what's left are (1) a handful of subtle bugs introduced *by* the new security plumbing, (2) scaling concerns that surface only under multi-worker deployment, and (3) the gap between "secure foundation" and "differentiated SOC product." This review focuses heavily on the third category — the user explicitly requested feature suggestions, and that is where the highest-leverage work now lives.

**Overall Rating:** Production-ready as a single-tenant analyst toolkit. Not yet differentiated as a platform. The next phase is breadth (integrations, workflows, output channels), not depth (more hardening).

## 2. New Findings (Not Present in Previous Review)

### 2.1 Bugs Introduced by New Security Code

| # | Finding | Location | Severity |
|---|---------|----------|----------|
| B-1 | `revoke_all_user_tokens` does not actually revoke active tokens. It inserts a sentinel JTI (`__all_before_<timestamp>`) into the revocation table, but `is_token_revoked()` checks for **exact JTI match**. A real token's JTI will never equal the sentinel, so deactivated users keep working tokens until natural expiry — defeating the purpose of the change. | `auth/models.py:501-512` vs `:494-498` | **High** |
| B-2 | `change_password` does not invalidate other active sessions. After a credential change (often the response to suspected compromise) any previously-issued access/refresh tokens remain valid for their full TTL. | `auth/routes.py:294-329` | **High** |
| B-3 | HSTS header only emitted when `request.is_secure` is true. Behind a TLS-terminating reverse proxy (the recommended deployment per `DEPLOYMENT.md`), Flask sees plain HTTP unless `ProxyFix` is wired up — so HSTS is silently never set in production. | `webapp/app.py:137-138` | **Medium** |
| B-4 | `X-XSS-Protection: 1; mode=block` is deprecated and was removed from modern browsers; OWASP and MDN recommend not setting it (it has been a source of XS-Leaks). | `webapp/app.py:127` | **Low** |
| B-5 | The legacy unsalted SHA256 API key code path remains in `lookup_api_key`. There is no migration step, no deprecation timeline, and no alert on legacy-format hits — so an old leaked database file with unsalted hashes is still a complete bypass. | `auth/models.py:433-438` | **Medium** |
| B-6 | `cleanup_expired_revocations()` and `rotate_audit_logs()` exist but are never scheduled. The revocation table grows unbounded and audit log rotation requires a manual `vlair audit rotate` invocation. | `auth/models.py:515-520`, `:568` | **Low** |
| B-7 | `get_audit_log` admin endpoint enforces `Role.SENIOR_ANALYST` minimum, not `ADMIN`. The audit log includes IP addresses, user agents, and resource paths — sufficient detail that senior analysts can profile their peers' activity. The docstring at the top of `routes.py:26` says `(ADMIN / SENIOR_ANALYST)` so this is intentional, but worth re-examining: audit logs are a privacy-sensitive surface, and least-privilege would limit them to `ADMIN`. | `auth/routes.py:617` | **Low** |

**Recommendation for B-1:** Either add a `revoked_at_for_user` column to `revoked_tokens` and check `MAX(revoked_at) > token.iat` in `is_token_revoked`, or store a per-user `tokens_invalidated_after` timestamp on the `users` table and compare against `iat` during validation. The latter is simpler and matches how "logout everywhere" is typically built.

### 2.2 Scaling / Production-Readiness Gaps

| # | Finding | Location | Why it matters |
|---|---------|----------|----------------|
| P-1 | Auth rate limiter is process-local (`defaultdict` + `threading.Lock`). Under gunicorn with `--workers 4`, each worker keeps independent counters — effective limit is 4× the configured value. A coordinated attacker can also stick to a single worker via affinity. | `auth/routes.py:83-103` | Defeats the brute-force defense in any real deployment |
| P-2 | Background task results are held entirely in memory (`TaskRecord.result: Any`). A single 50 MB PCAP analysis result × dozens of concurrent users × multiple workers = unpredictable RSS growth. No backpressure, no disk spill. | `webapp/tasks.py:32-39` | OOM risk in production |
| P-3 | `_ai_summarizer` is a module-level singleton, but `ThreatSummarizer` holds an SQLite connection lazily; not all SQLite operations are safe across threads in default mode. Webapp is multi-threaded by default. | `webapp/app.py:75-82`, `ai/summarizer.py` | Latent race / cache corruption |
| P-4 | Tool classes (`URLAnalyzer()`, `IntelligenceGatherer()`, etc.) are still instantiated per request — flagged in March, not addressed. With caching these classes do non-trivial work in `__init__` (DB connect, env-var read). | `webapp/app.py` (every endpoint) | Unnecessary overhead under load |
| P-5 | No `/metrics` endpoint, no structured logging, no health/readiness split. `DEPLOYMENT.md` discusses monitoring but provides no scrape target. | webapp/ | Operational opacity |
| P-6 | Coverage report excludes `webapp/*`, `pcap_analyzer.py`, `eml_parser.py`, `cert_analyzer.py`, `slack.py`, `teams.py`. The 75% gate covers ~half the surface area; the headline number is misleading. | `pyproject.toml:133-143` | False confidence |

### 2.3 Privacy & Compliance

| # | Finding | Location |
|---|---------|----------|
| C-1 | Audit log captures `user_agent` and `ip_address` indefinitely (rotation is opt-in, not automatic). For EU deployments this is GDPR-touching personal data without a documented retention policy or DSAR export path. |
| C-2 | No "data classification" markers on stored analysis results. A user uploading a PCAP containing employee credentials has no way to mark it sensitive, and no admin tooling to list/purge such uploads. |
| C-3 | The AI cache stores tool results keyed by content hash. Privacy stripping happens *before* the AI call, but the cache itself contains the sanitized prompt. There is no documented retention or purge command. |

### 2.4 What Continues to Be Done Well

- Privacy layer (`ai/privacy.py`) — still the standout piece of code in the repo.
- Deployment guide is concrete and actionable, not theatre.
- Backup-code implementation (`auth/models.py:293-373`) uses the same PBKDF2-with-salt pattern as API keys; one-time-use enforcement is correct.
- Security test suite (`tests/test_security.py`) actually exercises auth bypass, path traversal, and token revocation — not just smoke tests.
- Provider abstraction (anthropic / openai / ollama) makes BYO-AI realistic for air-gapped customers.

## 4. Prioritized Recommendations

### Immediate (Bug Fixes — Days, Not Weeks)

1. **Fix B-1** — `revoke_all_user_tokens` is currently a no-op. Add a `tokens_invalidated_after` timestamp on `users` and check it during JWT validation.
2. **Fix B-2** — invalidate other sessions on `change_password` (call `revoke_all_user_tokens` after the update).
3. **Fix B-3** — wire `werkzeug.middleware.proxy_fix.ProxyFix` into `create_app()` so HSTS actually fires behind a reverse proxy. Document the assumed proxy hop count in `DEPLOYMENT.md`.
4. **Fix B-4** — remove the `X-XSS-Protection` header (it is now harmful, not neutral).
5. **Schedule B-6** — register `cleanup_expired_revocations()` and `rotate_audit_logs(keep_days=90)` on a daily timer thread inside the webapp, *and* document them as systemd timers in `DEPLOYMENT.md` for non-Flask deployments.

### Next Sprint (Production Hardening)

6. Replace the in-memory rate limiter with a Redis-backed one (P-1). The existing `redis>=5.0.0` optional dep means no new dependency.
7. Spill background-task results to `~/.vlair/tasks/<task_id>.json` once they exceed a threshold (P-2). Read on demand from `GET /api/tasks/<id>`.
8. Add a `/metrics` endpoint exposing request count, latency histogram, AI calls, AI tokens, AI cost, task queue depth (P-5). Use `prometheus-flask-exporter`.
9. Switch the webapp from `print` to structured logging (`structlog` or stdlib `logging` with JSONFormatter), include `request_id` in every record (P-5).
10. Migrate legacy unsalted API key hashes to the new salted format on next successful authentication, log a warning when legacy format is matched, and add a deprecation date (B-5).
11. Cache tool instances at app-context level instead of per-request (P-4).
12. Re-include `webapp/*` and the three excluded analyzer modules in the coverage report; raise the gate to a number that reflects the actual covered surface (P-6).

### 5.2 Gaps

| Gap | Risk |
|-----|------|
| `webapp/*` excluded from coverage | The largest codebase area — and the one with the most security-sensitive code — is not measured |
| No integration tests across CLI ↔ webapp ↔ AI layer | A regression in `investigate/state.py` could break the SPA timeline (when added) without any test catching it |
| No load tests / concurrency tests | Background task queue behavior under burst load is unknown |
| No fuzzing of input parsers (`eml_parser`, `pcap_analyzer`, `deobfuscator`) | These accept attacker-controlled input by design — they are the highest-priority targets for fuzz coverage |
| AI provider swapping is not tested end-to-end | A breaking change in `openai>=1.0.0,<2.0.0` will surface only in production |

**Suggestion:** add `hypothesis` for property-based tests on the parsers, and a small `locust` config for load tests against the webapp. Both are low-effort to set up and would catch the missing categories.
